# 実測 JSON（`mdr-measures-1`）

上流（CAD・スキャン）と数量拾いの**唯一の契約**。上流は**解決済みの幾何**だけを書き、
拾い側は**幾何を一切計算しない**。幾何を 2 つの言語で書かないための線。

```json
{
  "schema_version": "mdr-measures-1",
  "source": "minicad",
  "plan_id": "room-0a3f",
  "name": "ワンルーム",
  "rooms": [
    {
      "id": "r1",
      "name": "居室",
      "floor_area": 19.42,
      "ceiling_area": 19.42,
      "perimeter": 17840,
      "height": 2400,
      "wall_area": 42.82,
      "openings": [
        {"id": "o1", "kind": "window", "width": 1690, "height": 1170, "sill": 800},
        {"id": "o2", "kind": "door",   "width": 800,  "height": 2000, "sill": 0}
      ],
      "furniture": [{"code": "sofa", "label": "ソファ", "count": 1, "item": "SOF-01"}],
      "finish": {"wall": "WC-1000", "ceiling": "WC-2000", "cornice": ""},
      "basis": {"height": "既定"},
      "basis_note": {"height": "階の既定 2400mm。天井高は持っていないので代用"}
    }
  ],
  "basis": {"swing": "未計測"},
  "basis_note": {"swing": "建具の開き勝手は図面の記号だけで、寸法として持っていない"}
}
```

## 上流で選んだ仕上げ（任意）

```json
"finish": {"wall": "WC-1000", "ceiling": "WC-2000", "cornice": ""},
"furniture": [{"code": "sofa", "label": "ソファ", "count": 1, "item": "SOF-01"}]
```

**書いてあれば `rules.toml` の `[[finish]]` より優先する。** 規則は「居室の壁は
量産クロス」という**部屋の種別ごとの決め打ち**で、3D や平面図の上で面を選んで
壁紙を決めたときに、その選択を書き留める先が無い。

`finish` のキーは面の種類（`floor` `ceiling` `wall` `baseboard` `cornice` `strip`）。
**知らない名前は断る。** `wal` と書いた選択を黙って無視すると規則の値が出てしまい、
「選んだのに反映されない」という、画面の上で一番気付きにくい壊れ方になる。

値の意味は `[[finish]]` と同じ 3 つ。

| | |
|---|---|
| 品目コード | それで拾う |
| 空文字 | **この面は拾わないと人が判断した**（報告に出さない） |
| 書いていない | まだ選んでいない。規則に落ちる |

**部屋名が規則に当たらなくても拾える。** スキャンは部屋名を持たないことがあり、
名前が合わないというだけで何も拾えないのでは、選んだ意味が無い。

`furniture[].item` も同じ。`[furniture]` に無い種別（`bed` など）でも、選んで
あれば拾う。**員数は変わらない**——選択が決めるのは品目コードだけで、面積も
個数もこの欄では動かない。

> `furniture[]` の選択は**種別ごと**に効く。1 個ずつ分けるなら `instances[]`
> （後述）で出す。面は `surfaces[]` で 1 枚ずつ分けられる。

## 置いてあるものの個体（任意）

```json
"instances": [
  {"id": "A749887E-…", "category": "chair", "label": "椅子",
   "extent": [663, 1328, 721], "basis": "実測",
   "asset": {"source": "abo", "id": "B071FMSY5S"}},
  {"id": "6475BFF4-…", "category": "bed", "label": "ベッド", "item": "BED-01"}
]
```

`furniture[]` が `{"code": "chair", "count": 4}` と種別で数えるのに対し、
こちらは**1 個ずつ識別子を持つ**。椅子 4 脚のうち 1 脚だけ別の品目にできるのは、
個体が並んでいるときだけ。**`instances` が無ければ従来どおり `furniture` の
種別集計で拾う。**

品目の決まり方は上から順に:

| | |
|---|---|
| `item` | 直に指した品目コード |
| `asset` | 3D の上で置き換えたカタログのアセット。**対応表で品目に引く** |
| `category` | 種別ごとの規則（`[furniture]`） |

**置換が種別より勝つ。** 人が 3D の上でカタログから選んだものが、「ソファと
いう種別」より具体的だから。`[furniture]` に無い種別（`bed` など）でも、
置換してあれば拾える。

**`asset` は `source` と `id` の両方が要る。** TemplateMaker は ASIN、
CaptureVisualizer は GLB のファイル名と、**識別空間が違う**。今はたまたま
重なっているが、カタログ源が増えれば bare な id は必ず衝突する。

**対応表はここに持たない。** 単価も品目も見積り側の持ち物なので、拾い側は
`(source, id)` を品目コードに引く呼び出しを受け取るだけ
（`takeoff.build(measures, rules, resolve)`）。

`resolve` が `None` を返したら「対応表に無い」で報告に出す。空文字は
「見積りに入れない」と人が決めた印なので黙って飛ばす。**この 2 つを畳むと、
書き忘れが「入れないと決めた」に化ける。**

`extent`（幅・高さ・奥行、mm）は見積書に添えるだけで、**値段は決めない**。

## 面の個体（任意）

```json
"surfaces": [
  {"id": "w0", "kind": "wall", "length": 3575, "height": 2408,
   "openings": ["w0-o0"], "finish": "WC-1000", "basis": "既定"},
  {"id": "w3", "kind": "wall", "length": 3135, "height": 2408,
   "openings": [], "finish": "WC-2000"},
  {"id": "__floor__",   "kind": "floor",   "area": 11.208, "finish": "FL-2000"},
  {"id": "__ceiling__", "kind": "ceiling", "area": 11.208, "finish": "WC-1000"}
]
```

**面が個体として id を持つことが、面ごとに仕上げを選べることの全て。** 室の
合計（`wall_area`）だけでは 4 面に別々の壁紙が貼れない。

`kind` は `wall` / `floor` / `ceiling` の 3 つだけ。**人が 3D の上でつつける面**
に限る。巾木・回縁・撤去は面から導く量でクリックできる面ではないので、室ごとの
`finish` のまま。

**壁は面積を持たない。長さと高さと、その面に属する開口の id を渡す。** 開口を
引くのは積算基準の規約（1 か所 `min_opening` ㎡以下は引かない）で、幾何を知って
いる上流の持ち物ではない。上流が先に引くと**規約が幾何の側に漏れ**、「拾い側は
算術と拾い方の規約だけを持つ」という線が崩れる。床と天井が `area` を持つのは、
引くものが無く面積が実測そのものだから。

**開口の実体は室の `openings[]` に 1 つだけ置く。** 面が持つのは id の参照だけ。
面にも実体を持たせると、同じ建具が 2 箇所から数えられて員数が倍になる。室に
無い id を指していれば断る——黙って無視すると、その壁が引かれずに過大になる。

`finish` が空なら室ごとの選択に落ち、それも無ければ `[[finish]]` の規則に落ちる。
**`surfaces` が無ければ従来どおり室の合計から 1 行で拾う。**

足し合わせると室ごとの答えに戻る。ここが割れると、面ごとに拾うか室ごとに拾うかで
金額が変わり、どちらが本当か説明できなくなる。

| 断る場合 | |
|---|---|
| 知らない `kind` | `wall` / `floor` / `ceiling` 以外 |
| `id` が空・重複 | 仕上げを当てる先が決まらない |
| 室に無い開口を指す | その壁が引かれずに過大になる |
| 壁の長さか高さが 0 | 数量が出ない面を黙って並べない |
| 床・天井が 2 枚以上 | 室に 1 枚だけ置く |

## 単位

| | |
|---|---|
| 長さ | **mm** |
| 面積 | **㎡** |

設計図書の慣習に合わせて長さは mm。スキャン側は m で持っているので、**変換は上流の責任**。
面積だけ ㎡ なのは、mm² だと桁が大きすぎて人が読めないため。

**切り捨てはしない。** 面積の表示を小数第 2 位で切り捨てるのは公正競争規約に基づく
**表示の規約**であって、計算の規約ではない。途中で切ると合計が合わなくなるので、
生の値を運び、**見せるときに切る**。

## 測ったものと仮定したものを区別する

`basis` が**この形式の中心**。同じ `wall_area` でも、実測の壁厚から出した値と、仮定した
壁厚 0.12m から出した値は、信じてよい度合いが違う。

**値そのものは素のまま書き、仮定した値だけを `basis` で名指しする。欄が無ければ実測。**

CaptureVisualizer が既に `area_source`（`"壁"` / `"床外形"` / `"外接矩形"`）で面積の
出どころを自己申告している。**その思想を形式全体に広げたもの。**

### 語彙は固定する

表記ゆれが混ざると機械で判定できない（単価表の税区分や認定欄と同じ作法）。

| 値 | 意味 | 強さ |
|---|---|---|
| `実測` | 測った、または作図された実値 | 5 |
| `推定` | 別の実測から導いた（床外形から面積） | 4 |
| `代用` | 別の量で代えた（天井高に壁高、内法に壁芯） | 3 |
| `既定` | 上流の既定値（壁厚 120、壁高 2400） | 2 |
| `外接` | 外接矩形など、**必ず過大**になる代用 | 1 |
| `未検出` | 検出の仕組みはあるが、この経路では走っていない | 0 |
| `未計測` | その量を持つ概念が上流に無い | 0 |

言い換えは `basis_note` に分ける。自由記述を `basis` に混ぜると語彙が壊れる。

### 未検出と未計測を分ける

**0 件を「無い」と読ませないため。** 開口 0 件には 3 つの意味がある。

| | |
|---|---|
| 欄が無い | 開口が本当に無い |
| `未検出` | 検出の仕組みはあるが、この経路では走っていない |
| `未計測` | その量を持つ概念が上流に無い |

**壁面積はこの 3 つで全く違う数になる。**

### 合成は最弱が勝つ

拾い側は 1 つの数量を作るのに使った入力の根拠を集め、**一番弱いものをその数量の根拠と
する**。仮定を 1 つでも混ぜた数量は、その仮定の精度までしか正しくない。

平均や加重は採らない。「根拠 3.7」は誰にも説明できず、**見積書の脚注に書けない**。

## 部屋を分けられない上流

スキャンは壁の集まりしか返さず、閉領域を列挙できない。そのときは
**部屋 1 つとして書き、`basis.partition` に `"未計測"` と書く。**

`未分割` のような専用の語は足さない。**根拠の軸が 2 本になって合成できなくなる。**
形式としては多室を表現できるので、上流が対応した日に形式を変えずに済む。

## 入れ子（柱型・PS）の控除

**上流の責任。** 幾何を知っているのは上流だけ。拾い側は受け取った `floor_area` を
そのまま信じる。

## 開口

`sill`（床からの下端）が**巾木を引くかどうかを決める**。床まで届く建具（`sill == 0`）は
周長から引き、腰窓（`sill > 0`）は引かない。

`kind` は上流の語彙をそのまま運ぶ。MiniCAD は 10 種（`door` / `window` / `slidingDouble` …）、
スキャンは 3 種（`door` / `window` / `opening`）。**拾い側は `sill` と寸法しか見ない**ので、
語彙の違いは問題にならない。
