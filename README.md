# QuantityTakeoff

図面とスキャンの**実測から内装の数量を拾う**。拾った数量は
[InterierEstimation][est] がそのまま食える形で出る。

```bash
uv sync
uv run takeoff run examples/minicad.measures.json --rules examples/rules.toml
```

```
ワンルーム 内装改修（CAD から）
基準 公共建築数量積算基準 令和 5 年改定（見本）

部屋           面       品目                 数量 単位
=======================================================
居室           床       FL-2000             19.42 ㎡
居室           天井     WC-2000             19.42 ㎡
居室           壁       WC-1000            31.041 ㎡
居室           巾木     BB-0100             14.23 m
居室           撤去     CL-0100            50.461 ㎡
居室           建具     DR-0100                 1 箇所
...
```

外部依存は無い。標準ライブラリだけで動く（設定の TOML は `tomllib`）。

## 何を持ち、何を持たないか

**幾何は計算しない。** 面積も周長も壁の正味長も、それを知っている上流（CAD・スキャン）が
解決して[実測 JSON](docs/measures.md) に書く。ここは**算術と拾い方の知識だけ**を持つ。

幾何を 2 つの言語で書くと、**同じ部屋の面積が道具によって違う**という最悪の形で破綻する。

| | |
|---|---|
| 持つ | 積算基準の規約、仕上げの割り当て、員数の集計、報告 |
| 持たない | 面積・周長・壁の区間の計算、部屋の検出、単価、金額 |

```
MiniCAD ──────┐
              ├→ 実測 JSON ─→ QuantityTakeoff ─→ 数量リスト ─→ InterierEstimation
CaptureVisualizer ┘                                                   ↓
                                                                   見積書
```

[est]: https://github.com/24th-garnet/InterierEstimation

## 入力 1 — 実測 JSON

上流との**唯一の契約**。形式は [docs/measures.md](docs/measures.md)。

**長さは mm、面積は ㎡。** 設計図書の慣習に合わせ、変換は上流の責任にする。

**`basis` がこの形式の中心。** 同じ壁面積でも、実測の壁厚から出した値と仮定した壁厚から
出した値では信じてよい度合いが違う。[CaptureVisualizer][cv] が既に `area_source`
（`壁` / `床外形` / `外接矩形`）で面積の出どころを自己申告しているので、**その思想を
形式全体に広げてある**。

```json
"basis": {"wall_area": "既定"},
"basis_note": {"wall_area": "RoomPlan は壁厚を返さない。作図上の 0.12m"}
```

**語彙は固定する** —— `実測` / `推定` / `代用` / `既定` / `外接` / `未検出` / `未計測`。
表記ゆれが混ざると機械で判定できない。言い換えは `basis_note` に分ける。

**`未検出` と `未計測` を分けるのは、0 件を「無い」と読ませないため。** 開口 0 件には
3 つの意味がある——本当に無い（欄なし）、検出していない（`未検出`）、概念が無い
（`未計測`）。**壁面積はこの 3 つで全く違う数になる。**

**合成は最弱が勝つ。** 1 つの数量を作るのに使った入力の根拠を集め、一番弱いものをその
数量の根拠とする。仮定を 1 つでも混ぜた数量は、その仮定の精度までしか正しくない。
平均や加重は採らない——「根拠 3.7」は誰にも説明できず、見積書の脚注に書けない。

```
仮定に頼った数量が 2 行ある。
  既定 2 行
```

実測でない根拠は、見積書の注記にそのまま出る。

```
量産クロス  35.02 ㎡
  └ 撮影範囲 壁面積。開口 2 箇所を差し引き（根拠 既定）
```

[cv]: https://github.com/24th-garnet/CaptureVisualizer

### 部屋を分けられない上流

スキャンは壁の集まりしか返さず、閉領域を列挙できない。そのときは**部屋 1 つとして書き、
`basis.partition` に `未計測` と書く**。`未分割` のような専用の語は足さない——根拠の軸が
2 本になって合成できなくなる。形式は多室を表現できるので、上流が対応した日に形式を
変えずに済む。

```
※ 上流が部屋を分けていない。撮影範囲全体を 1 室として拾っている
```

## 入力 2 — 拾い方の設定

**品目コードはリポジトリに持たない。** どの面にどの仕上げが来るかは案件ごとに違い、
品目コードは会社ごとの単価表に紐づく。手元の TOML を指して使う（`.gitignore` 済み）。

```toml
standard = "公共建築数量積算基準 令和 5 年改定"

[deduct]
min_opening_area = 0.5

[[finish]]
rooms = ["居室", "洋室"]
floor = "FL-2000"
wall = "WC-1000"
ceiling = "WC-2000"
baseboard = "BB-0100"
cornice = "CN-0100"
strip = "CL-0100"

[[finish]]
rooms = ["洗面", "脱衣"]
floor = "FL-3000"
wall = "WC-1000"
ceiling = "WC-1000"
baseboard = "BB-0100"
cornice = ""            # 水回りに回り縁は回さない

[fittings]
door = "DR-0100"
window = "WD-0100"
opening = ""            # 建具なしの出入口。拾うものが無い

[furniture]
sofa = "SOF-01"
sink = ""               # 洗面台は設備工事。内装の数量には入れない
```

**推定しない。**「洗面脱衣だからクッションフロアだろう」とこちらが決めると、外れたときに
見積書のどこが間違っているのか分からなくなる。**対応は人が書く。**

**部屋名は部分一致で、先に書いたものが勝つ。** 正規表現にしない —— パターンが読めなく
なったとき、どの部屋がどれに当たるのかを人が目で追えなくなる。

### 空文字は「拾わない」という判断

**3 つの状態を分ける。**

| | |
|---|---|
| 品目コード | 拾う |
| **空文字** | **この部屋にその面は無い、と人が判断した** |
| 書いていない | **まだ誰も見ていない** → 報告に出る |

これが無いと、巾木の無い部屋がいつまでも「品目コードが無い」と報告に出続けて、
誰も直さなくなる（[InterierEstimation][est] の単価表が認定欄に `対象外` を持つのと同じ）。

### 拠った基準を書かせる

`standard` は必須。**基準は版で記述が変わる**（公共工事は国交省基準、民間は
建築数量積算基準・同解説）。単価表に `source` と `as_of` を持たせたのと同じ理由で、
**後から根拠をたどれないと検算できない**。拾いの結果にも残る。

## 積算基準の規約

公共建築数量積算基準（国交省、令和 5 年改定）に拠る。**規約として固定し、数字だけを
設定で変えられるようにする。**

| | |
|---|---|
| 開口の欠除 | **1 か所 0.5 ㎡以下は差し引かない。** 現場で加工できないものは 0.1 ㎡という運用もあるので閾値は設定 |
| 巾木・回縁による壁の欠除 | **幅・高さを問わず無いものとする。** 壁面積から巾木の高さを引かない |
| 巾木の長さ | 周長から**床まで届く建具の幅だけ**を引く。腰窓は巾木が回るので引かない |
| 回縁の長さ | 周長そのまま。**建具は天井まで届かない** |
| 撤去 | 壁（開口控除後）＋ 天井。既存仕上げを剥がす面 |
| 数量の丸め | **第 3 位を四捨五入。** 切り上げない（過大な見積りは説明できない）、切り捨てない（材料が足りなくなる） |

**ロス率は見ない。** 切り代・張り代は単価表の `loss` 列が持っているので、拾いで割増すと
二重に掛かる。ここが出すのは**設計図書の数量**であって、発注数量ではない。

**面の単位は `rules.SURFACES` が唯一の出どころ。** 面積は ㎡、長さは m、員数は箇所／個。
単価表の単位と合っている必要があるので、2 箇所に書かない。

## 当たらなかったものを落とさない

**黙って落とすと、拾えなかったのか拾って 0 だったのかが区別できず、見積りが静かに
足りなくなる。** 単価の付かない行を落とさないのと同じ判断。

```
品目コードの当たらなかったものが 1 件ある。その分だけ数量が足りない。
  洗面脱衣      家具    sink に品目コードが無い
```

自動で回すなら `--strict` で失敗にできる。当たり外れだけ見るなら `check`。

```bash
uv run takeoff check measures.json --rules rules.toml
uv run takeoff run measures.json --rules rules.toml --strict
```

## 書き出し

```bash
uv run takeoff run measures.json --rules rules.toml --format json -o quantities.json
```

**数量は文字列で出す。** 受け手は `Decimal` で読み直すので、JSON の数にすると float を
経由した読み手が末尾を濁らせる。

**同じ品目コードが 2 行あっても合算しない。**「居室の壁」と「洗面脱衣の壁」は同じクロス
でも別の行として見せたい。合算すると見積書から現場が消える —— 受け手が持っているのと
同じ判断。

## モジュール

| | |
|---|---|
| `measures.py` | 実測 JSON の読み込みと検証 |
| `rules.py` | 拾い方の設定。品目コードの対応 |
| `takeoff.py` | 実測 × 拾い方 → 数量。**純関数だけ。ファイルも時刻も見ない** |
| `report.py` | 端末の表 / 数量リスト JSON |
| `cli.py` | コマンド |

## テスト

```bash
uv run pytest tests -q     # 66 件
```

積算基準の規約（開口の欠除・巾木の引き方・回縁）は、**数字を直したら落ちる**ように
書いてある。そのための**固定の実測をテストの中に持っている** —— 見本に乗せると、
見本を作り直すたびに巻き添えで落ち、規約が変わったのか見本が変わったのかが分からなくなる。

見積モジュールまで通る通しのテストもあるが、`InterierEstimation` が隣に無ければ飛ばす。
